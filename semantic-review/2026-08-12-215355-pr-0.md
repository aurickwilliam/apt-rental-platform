# Mobile resource-query migration and focused reads

Batch 2 replaces repeated mobile reads with TanStack Query resources keyed by the resolved internal `public.users.id`, moves favorite feedback into screen callers, and extracts the dashboard count workflow. Favorites now use a virtualized `FlatList`, maintenance removes its competing mount fetch, and the search count switches from exact to estimated. The new tenancy subscription correctly avoids unrelated updates once an active tenancy is known, but it no longer observes the matching event that creates or replaces that tenancy. No Batch 3 media or apartment-image contract work is present: the only image-adjacent change invalidates the existing current-user cache after a successful avatar/background update.

Watch for: **confirmed** concurrent favorite failures can roll the shared cache back over a later successful toggle; **confirmed** a tenant with no cached active tenancy cannot receive a relevant approval/replacement realtime update; **confirmed** an estimated database count is rendered as an exact result total without the required measurement gate.

**Verdict**: NEEDS_CHANGES

## High-level view

The shared current-user query resolves the auth identity to the internal user ID once, and the favorites, tenancy, and dashboard keys include that internal ID. Explicit sign-in and sign-out paths clear the shared client, while profile and avatar/background updates invalidate only the identity entry.

Favorite toggles update the tenant-scoped ID list optimistically and leave notifications to the apartment, search, and favorites screens. The rollback is not isolated to the mutated apartment, however, so overlapping requests can restore an obsolete whole-list snapshot and conceal a successful server-side change.

Tenancy refreshes are explicit query refetches, so they bypass the freshness window. Realtime subscriptions narrow payment and tenancy events to the loaded tenancy, which eliminates unrelated refreshes but also means there is no subscription at all while the cache contains no active tenancy.

The dashboard reads apartment IDs once before starting the three independent count reads in parallel; maintenance now has one focused lifecycle path; and the favorites list owns scrolling and pull-to-refresh. The search result counter has a different contract: PostgREST may return an estimate, while both visible count surfaces continue to state an exact number of results.

## Favorite cache rollback crosses mutation boundaries

`useFavorites.toggleFavorite` captures the entire `['favorites', tenantId]` list, applies an optimistic add or remove, and restores that captured list if its request fails. Two quick toggles can therefore race: removing A saves `[A]` and writes `[]`; adding B then saves `[]` and writes `[B]`; if the B insert succeeds but the A delete fails, A’s error handler restores `[A]`. The server now contains both A and B, while the shared favorites cache loses B. The successful B mutation has already invalidated `['favorite-apartments', tenantId]`, so an in-flight list refetch can also derive an empty or incomplete list from the transient cache and no failure path invalidates it again.

This is **confirmed** from `apps/mobile/hooks/favorites/useFavorites.ts`: cancellation protects an in-flight query read, not another toggle writing the same query key. The current tests prove the one-toggle optimistic result only; they do not exercise overlapping success/failure outcomes. Roll back only the affected ID against the latest cache state, use a mutation queue keyed by tenant/apartment, or invalidate/refetch the exact favorites and favorite-apartments keys after an error so the client converges on the authorized server state.

## Tenancy filtering drops the event that establishes the resource

`useTenancy` registers both realtime filters only after `tenancy?.id` exists. When a tenant has no active tenancy, the query returns `null`, the effect returns before creating a channel, and a subsequent insert or a replacement tenancy activation has no listener. `refetch` would force a network read, but the tenant rental/current-apartment consumers do not expose it through a refresh action; foreground refetch is also freshness-dependent. The result is a screen that can remain in its no-tenancy state while the database contains an approved active tenancy.

This is **confirmed** in `apps/mobile/hooks/tenancy/useTenancy.ts` and by the current consumer set. The existing tests cover only an unrelated tenancy event after `TENANCY_ID` is already loaded, so they cannot reveal this transition. Subscribe to `tenancies` with `tenant_id=eq.${tenantId}` whenever the internal tenant identity is available and conditionally invalidate `['tenancy', tenantId]` after verifying the payload’s tenant ID. The payment subscription can remain scoped to the resolved tenancy ID; a new test should begin with `null`, deliver a matching tenancy insert/update, and assert that the exact query refetches.

## Search labels claim certainty after changing to an estimate

The first search page changed `count: "exact"` to `count: "estimated"`, but `SearchFiltersBar` and `FilterBottomSheet` still render strings such as `"42 apartments found"` and `"42 results found"`. PostgREST’s estimated mode may return a planner estimate rather than the exact number, so these labels can be false even though the page contents and pagination still work.

This is **confirmed** by `apps/mobile/app/(tabs)/components/search/useSearchLogic.tsx`, `SearchFiltersBar.tsx`, and `FilterBottomSheet.tsx`. The Batch 2 plan permits estimated/no explore counts only after Batch 0 measurement supports it; `.kiro/specs/audit-fix/batch-0-evidence.md` explicitly records that those measurements were unavailable. Preserve the exact count until that gate closes, or make the count optional/approximate in every user-visible surface and add coverage for the chosen semantics.

Focused cache tests and the complete mobile Jest suite pass (18 suites, 129 tests). **Not tested:** the failed-A/successful-B favorite race, an active-tenancy transition from a cached `null`, and the selected user-visible approximate-count contract.
