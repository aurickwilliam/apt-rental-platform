## Project

Rental management platform for the Philippine market (CAMANAVA area focus), serving tenants and landlords across web and mobile.

## Stack & Monorepo Structure

- pnpm@10.34.5 monorepo (Node 22.17.0 — see `.nvmrc`), workspace roots: `apps/*`, `packages/*`
- Backend: Supabase (Postgres, Auth, Realtime, Storage)
- CI: one required `ci` job (`.github/workflows/ci.yml`) runs population-command tests, mobile lint + jest and web lint + typecheck + tests; no formatter config. `apps/mobile` has a Jest suite (`jest-expo` + `@testing-library/react-native` + `fast-check`, also covering `packages/passport` and `packages/utils`) via `pnpm --filter mobile test`; `apps/web` has `node:test` suites for pure helpers in `lib/*.test.mjs` via `pnpm --filter web test`

Portal layouts pass their server-known roles as `SettingsModal initialRoles` so tenant tabs render on first paint; the client profile wins once settled.

Complete profiles and both acceptance records commit only through the caller-bound `complete_web_registration` transaction (`service/registrationService.ts`), never separate profile/acceptance writes or Auth metadata. Keep it SECURITY INVOKER so profile RLS, column grants and guards remain active; its narrow definer helper writes only the caller's acceptance history. Match policy revisions with a migration before web deployment. Do not add universal acceptance triggers or change mobile signup: completed/legacy accounts stay usable without records. See `docs/web-registration-acceptance.md`; regression command: `pnpm db:web-registration:test` (also runs in CI).
- Password recovery (`app/(auth)/forgot-password`) mirrors mobile with server actions in `app/(auth)/actions/password-recovery.ts` (`@repo/supabase/server`): request/resend → verify (`"ready" | "google_only"`) → update → `signOut({ scope: "global" })` → `/forgot-password/updated`. The email and code steps share one page and the email stays in component state, never the URL. Before verifying, the action sets the HTTP-only `apt-password-recovery` marker cookie (start time inside, 400-day lifetime like the Auth cookies; a recovery older than 30 minutes is abandoned). `recoveryRouteDecision` in `@repo/supabase/password-recovery` (pure, tested in `lib/password-recovery.test.mjs`) lets a marked session use only `/forgot-password/reset-password`; the middleware signs it out anywhere else. Background requests (`Sec-Fetch-Dest` not `document`; Next.js strips its own router headers before the middleware) get a 204 instead of a sign-out, so prefetches never end a reset. Server actions skip the middleware, so `updateRecoveredPassword` re-checks the marker itself. Actions that end in `redirect()` reject the client's promise with Next's redirect signal: call them inside a transition and `unstable_rethrow` in the `catch`. A server action that sets cookies re-renders the current page, so the reset page renders a "session ended" view rather than redirecting. Middleware redirects that sign out must copy `supabaseResponse` cookies onto the redirect. The marker is a journey guard, not a security boundary. See ARCHITECTURE.md §4.3.

The server action `app/(auth)/actions/change-password.ts` refuses while the recovery marker is present (server actions skip the middleware), then runs `changePasswordWith(supabase.auth, …)` from `@repo/utils`. It returns only a `PasswordErrorReason`, and the form places it with `getPasswordChangeErrorField`. The actions in `app/(auth)/actions/change-email.ts` refuse while the recovery marker is present and for suspended accounts, then run the shared `requestEmailChangeWith` / `verifyEmailChangeCodeWith` / `resendEmailChangeCodesWith` steps from `@repo/utils` (`emailChange.ts`): current-password check with `signInWithPassword`, `updateUser({ email })`, dual-inbox `verifyOtp({ type: "email_change" })` with completion confirmed by re-reading Auth, profile sync via the caller-bound `sync_my_profile_email()` RPC, then `signOut({ scope: "others" })`. The camera is URL state (`lat`/`lng`/`z`, `app/browse/lib/map-view.ts`); search and filter changes there must update the URL with `window.history.replaceState(null, …)` (via the `navigate` prop of `SearchContainer` / `FilterDrawerButton`), never `router.replace` (a page-segment query change remounts the page and drops the map) and never with `window.history.state` (Next ignores its own state, so `useSearchParams` would not update). Pins are HTML overlays (`useMapPins`), not Google markers, and the selected listing's card is a portal into an anchored overlay in the float pane (`useMapPopup`); the page owns favorites state (`useFavoriteActions`) and passes it to both the list and that card. Routes and links come from `lib/public-profile.ts` (`landlordProfileHref`, `tenantProfileHref`); the shared read-only components live in `app/components/profile/public/` (never reuse the editable `ProfileHeader`). The tenant page's verified-document chips come from `getVerifiedPassportSlots` (`@repo/passport`); RLS lets a landlord read passport rows only for pending/approved applicants, so an empty list means "nothing visible", never "unverified". The landlord page shows the mean of individual review ratings (`summarizeReviewRatings`, never an average of listing averages) with its 1–5 distribution, and counts verified listings with `summarizeListingVerification`; review attribution ("Stayed at …" plus the stay range) comes from the review's `tenancy_id`, joined only for signed-in viewers because anonymous tenancy policies make the whole review request fail (`apartmentReviewSelect`). See DESIGN.md §11 and ARCHITECTURE.md §12.1.
- Profit & planning reads go through one in-memory read cache (`lib/landlord-finance-cache.ts`, framework-free and node-tested): keys start with the owner id, a value under 60s old is reused without a request, one up to 5 minutes old paints immediately while it revalidates, concurrent reads share one load, failures are never cached, and every successful write clears the owner's entries. The report (`useLandlordFinances`), the month picker's indicators (they reuse cached reports), and the first page of the expense and collection lists read through it; `useFinanceExpensesPrefetch` warms the Expenses tab once the report shows. An explicit Refresh invalidates its own key so it always reaches the network. Add new finance reads through this cache rather than a bare fetch, and never share a key across owners.
- `pnpm-workspace.yaml` `overrides` carry security patches only (`@babel/core`, `@hono/node-server`, `@isaacs/brace-expansion`, `@xmldom/xmldom`) — no version pins for app deps
- Notification consumers (web) reuse `useNotifications`: one account-keyed `NotificationFeedStore` (`lib/notification-feed-store.ts`) owns the latest-50 query, in-flight deduplication, Realtime channel, and optimistic read flags. Its `useSyncExternalStore` snapshot is the shared-feed exception to per-consumer `useAsyncResource`; do not add independent notification queries or item-level subscriptions. Sidebar activity is selected by the typed mapping in `lib/sidebar-notification-activity.ts`, not by route visits or message-body matching. It reflects `notifications.is_read`, not chat unread counts, Passport readiness, or pending admin workload. Only accessible configured nav items can display a dot. Dispose account feeds when their last consumer leaves; reject late reads/writes from retired generations.
- Message-notification grouping (web and mobile) is presentation-only, applied by the drawer (web) and `NotificationList` (mobile) before the shared local-date grouping: consecutive ordinary chat messages from one sender collapse into one summary (`groupNotificationFeed` in `@repo/utils`, `notificationGroups.ts`, with the row sentence/preview composition in `notificationRow.ts` — rolling 15-minute chain window, identity = conversation + sender; reactions, other events and rows with a missing/ambiguous identity stay individual). The summary previews the newest message and opens the exact conversation (`?conversation={peerId}:{apartmentId|'none'}` on both message pages, resolved by `selectPortalConversation`); it batch-acknowledges the group's unread rows — one `markNotificationsRead` batch — only when the payload resolved that conversation, never on the inbox fallback. Expansion is `NotificationDrawer`-local state keyed by the group's oldest loaded member, so Realtime arrivals keep a group open. The unread badge, sidebar dots and per-row read behavior stay record-based; never mark rows read from navigation alone.
- Chat (web) runs one Realtime channel per open conversation, owned by `app/components/chat/useConversationRealtime.ts` and shared by both portals: `chat` INSERTs from the contact, `chat` UPDATE read receipts (rows whose `receiver_id` is the contact), `chat` DELETEs for unsends (unfilterable, so ids outside the thread are ignored; web unsend also broadcasts `message_deleted` to mobile's `chat:msg:{key}` topic), typing presence, and a resync on re-join/refocus whose rows merge through `conversationEvents.ts` (`mergeIncomingMessage`, `reconcileMessages`) so a refresh can never drop a newer realtime arrival, an optimistic send, or paged history. The channel topic is the users-pair id because that topic doubles as the presence room; a leftover channel for the same topic is closed before resubscribing (`supabase-js` dedupes channels by topic and refuses bindings on a subscribed one). Bind only tables that are in the `supabase_realtime` publication — a single unpublished binding (e.g. `chat_reactions` today) fails the whole join and silently disables the valid bindings too, which is why reactions stay refresh-based until that publication change is reviewed. The Messages list has its own single per-user channel, `useConversationListRealtime` (`messages-list:{userId}`: `chat` INSERTs received and sent), shared by both portals; it updates a row's preview/time/unread, re-sorts (pinned first, then latest message) and toasts for chats that are not open. Never add another per-consumer list subscription. List actions (pin, archive, mute, mark read/unread, block, report) go only through the caller-bound RPCs `set_conversation_preference`, `mark_conversation_read`, `block_user`/`unblock_user` and `report_user` (`app/components/chat/conversationActions.ts`, `useConversationActions`) — never write `conversation_preferences`, `user_blocks` or `user_reports` directly; report reasons are the shared `USER_REPORT_REASONS` in `@repo/utils`.

Chat/reactions are never implicitly shared: a valid `data.recipientPortal` wins; otherwise `notificationService.fetchNotifications` resolves legacy rows with one bounded `apartments(id, landlord_id)` lookup through `lib/chat-notification-audience.ts` before publishing the account feed. The recipient owning that apartment means Landlord; the peer owning it means Tenant. Missing/conflicting context stays `unresolved`, excluded from every portal's rows/counts/acknowledgments without deleting or writing the record. `resolvedChatAudience` is a read-time field only, not persisted metadata; never infer it from memberships, selected portal, message preview or an active tenancy. Admin review submissions and explicit Admin metadata may reach Admin; consumer subtypes and the unknown-event fallback may not. Keep audience filtering in `useNotifications` before grouping, dates, badges and mark-all-read, and reuse that classification for sidebar activity. Portal changes reset drawer-local expansion/filter state, never the account-keyed feed or its subscription.

### `apps/mobile` — React Native (Expo 57), Expo Router
- Native projects are generated, never tracked: `ios/` and `android/` are gitignored, so anything a config plugin writes (`Info.plist` permission strings, manifest permissions, native config) reaches an installed dev client only after `npx expo prebuild` **and** a native rebuild. Autolinking/`pod install` and Metro reloads do not apply plugin output; after changing plugin options in `app.config.js`, run `npx expo prebuild --clean` in `apps/mobile`, then `expo run:ios` / `expo run:android` (or a new EAS build). This is why Save as photo needs the `expo-media-library` plugin's `savePhotosPermission` (`NSPhotoLibraryAddUsageDescription`) in the generated project.
- Styling: **Uniwind** utility classes — NOT NativeWind (migrated away; don't reintroduce)
- Routes only live in `app/`: Expo Router treats every other file there as a route, warns when one lacks a default export and adds a phantom typed route, so helper modules belong in `constants/`, `utils/`, `hooks/` or `service/`. `tests/app-routes.test.ts` fails when a file under `app/` cannot be exported as a screen.
- UI: **HeroUI Native v3** (`heroui-native`). Its shared `Input` is patched in `patches/heroui-native@1.0.8.patch` for consistent borders and single-line text alignment on iOS and Android (DESIGN.md §10). `TextArea`, `SearchField` and `InputGroup` inherit it; multiline inputs retain their layout. Re-check the patch when upgrading `heroui-native`; `components/inputs/HeroUIInput.test.tsx` exercises the installed patch rather than a HeroUI stub.
- Bottom sheets (`heroui-native` `BottomSheet`): the sheet only snaps open on a closed → open transition (`BottomSheetContentContainer` in the installed package records `isOpen` on mount and snaps on change). Keep every sheet mounted and drive it with an `isOpen` boolean — never conditionally mount one already open, and never key-remount one into the open state (both render it off-screen). Because sheets stay mounted, an open-once draft has to be reseeded from its request on each open and its form state must never outlive the open (see `components/finance/` entry sheets). A sheet that hosts a control opening a React Native `Modal` (e.g. `DateField`'s iOS picker) must pass `disableFullWindowOverlay` to `BottomSheet.Portal`: on iOS the default full-window overlay draws above native modals, so the picker would open invisibly behind the sheet. Every sheet opens at an explicit snap point (`snapPoints`, never content-measured `enableDynamicSizing`): gorhom only builds the content-sized detent after layout is measured, so a sheet that opens before that detent exists settles short and clips its last row — picker sheets pass a height for short lists and otherwise fall back to a tall default (`FinanceSelect`).
- Icons: `@tabler/icons-react-native` — NOT `lucide-react-native` (migrated away 2026-08-29; dependency removed from `apps/mobile/package.json`)
- State: server state via **React Query** (`@tanstack/react-query`) — single `QueryProvider` at the root layout, shared client in `utils/queryClient.ts`; Zustand for client state only (`stores/`)
- Apartment-review readiness is shared with web through `@repo/utils` `isReviewStayEligible` (three calendar months, month-end clamped, or lease end reached); the database remains authoritative. The mobile review-unlock prompt is one account-keyed gate in the tenant tab shell, shown only on foreground Rentals. Its bounded read uses React Query under Auth ID + internal tenant ID, requires an active tenancy in both the query and selector, excludes reviewed/hidden/deleted stays, and rejects retired account callbacks. Never fall back to a historical apartment when the active stay is ineligible or dismissed; eligible past stays remain available through manual review screens. Dismissals are per-device AsyncStorage entries scoped to Auth ID + tenancy, not server data or notifications. Never clear all device storage to reset a prompt; the development-only helper is documented in `docs/mobile-review-unlock.md`. See DESIGN.md §14 for the UI.
- Auth: PKCE flow with `@react-native-async-storage/async-storage`; the platform-aware Supabase client lives in `@repo/supabase` (`packages/supabase/src/client.ts` handles RN/SSR branching)
- Babel: `react-native-reanimated/plugin` in `babel.config.js`
- Keyboard: `react-native-keyboard-controller` (Expo-pinned; native, so adding or upgrading it needs a dev-client rebuild). `KeyboardProvider` wraps the root layout; `ScreenWrapper scrollable` uses its `KeyboardAwareScrollView`. Screens that scroll programmatically take a `ScreenWrapperScrollRef` (standard ScrollView API, e.g. `scrollTo`) and never import the keyboard library. `react-native-keyboard-aware-scroll-view` was removed 2026-10-13 (it logged `viewIsDescendantOf() noop` errors under the New Architecture).
- Chat images (mobile): pasting uses the keyboard's own Paste button, never a menu entry. `ChatBox` wraps the input in `expo-paste-input`'s `TextInputWrapper`, which intercepts image pastes natively and hands back local file URIs that go through the normal attachment staging (`pastedImageMimeType`); text pastes insert as usual. The module is native and autolinked: adding it needs a dev-client rebuild (`expo run:ios` / `expo run:android`), and it does not run in Expo Go. Hold-menu "Copy image" goes through `service/chat/clipboardImage.ts` (download to cache, base64 to `expo-clipboard`). Web mirrors this: the composer stages files from the `paste` event (`MessageInput`), unless the clipboard also carries text.
- Pull-to-refresh wrappers must forward the native control's ref, `style` and `children`: Android `ScrollView` clones the control with its native scroll view as the child, and Gesture Handler lists inject a ref. Dropping any of these breaks the native scroll/gesture attachment. Keep the shared `PullToRefreshControl` contract covered by its regression test; visual behavior is defined in DESIGN.md §15.
- Services: `service/` mirrors the `hooks/` domain folder layout (e.g. `service/chat/chatService.ts`, `service/media/privateMediaResolver.ts`); tests co-locate in their domain folder, imported via direct file paths (no barrels)
- Profile editing is shared by both portals at `/edit-profile`: keep the draft local and initialize it once per auth account, never on background refetch. `useEditProfile` owns validation and the save mutation; `service/auth/profileService.ts` picks photos locally, uploads compressed binary photos to new account-folder paths on Save, then updates the editable fields and photo references in one caller-owned row write. Never overwrite the current photo before the row write; never delete uploads after a write with an uncertain outcome. Locked identity/email fields, roles and account status never enter the update. See ARCHITECTURE.md §4.4 and DESIGN.md §16.
- Profile details on sign-up (`app/(auth)/complete-profile`, new email account) and onboarding (`app/(auth)/finish-profile`, an account that already exists: first Google sign-in, interrupted sign-up, or an incomplete profile opened from the profile tab) share one form: `hooks/auth/useProfileDetailsForm` (personal + address fields, validation, scroll-to-first-error, `toRow()` for the `users` columns) rendered by `components/profile/ProfileDetailsFields`. Each screen keeps only what is its own: sign-up adds `NewPasswordFields` and submits through `useSignUpProfile` (`signUpService`, then the registration store → code verification, where the profile row is written); finish-profile adds the role tab and submits through `useFinishProfile` → `service/auth/finishProfileService.ts` (insert when no row, else `set_onboarding_role` + update). Build links to finish-profile with `finishProfileRoute` and read them with `readFinishProfileParams` (`service/auth/finishProfileRoute.ts`), never a hand-written pathname. Whether a signed-in account still needs onboarding is `needsProfileOnboarding` (`@repo/utils`: no mobile number and still `unverified`, as on the web page); a Google display name becomes first/last name through `splitFullName`, and the Auth `full_name` is built with `joinFullName`. Birth dates move between the picker and the form with `toBirthDateValue` / `fromBirthDateValue` (local time) — never `toISOString()`, which shifts the day before 8 AM in Manila. The screen owns the scroll ref it passes to the form (the refs lint rule rejects a ref inside the shared form object). Import these three hooks by path, not through the `hooks/auth` barrel: `useFinishProfile` loads the navigation library, which breaks every Jest suite that touches the barrel. ## Supabase Conventions

- `public.users` has both `user_id` (→ `auth.uid()`) and internal `id` UUID PK. **All RLS policies and FK relationships use the internal `id`**, resolved via:
  ```sql
  (SELECT id FROM public.users WHERE user_id = auth.uid())
  ```
- Dual-role profiles may act in either portal, but a tenant must not transact with an apartment owned by the same internal `users.id`. Database triggers enforce this for applications, visits, favorites, reviews, tenancies, and payments; apartment chat participants cannot be the same user. Client guards only improve feedback and must not replace these checks.
- New tenant-side records and changes to their tenant/apartment/landlord relationship require a current tenant membership (`tenant` in `users.roles`), enforced by the `require_tenant_membership_for_new_transaction()` triggers. Admin membership grants nothing and never adds consumer access, but it no longer cancels a held tenant role: mixed admin/tenant profiles transact like any tenant (parity with mixed landlord finances), while admin-only profiles have zero consumer access. Historical rows remain readable and can be cancelled/rejected without granting a new role; approval that creates a new tenancy still requires tenant membership. Do not infer a new role from historical activity, and never exempt admins in new tenant-side guards.
- `public.users.roles` (`text[]`) and `account_status` are server-managed. Client profile UPDATE grants cover only editable fields; registration INSERT is restricted to tenant/landlord with `unverified` status. Google OAuth users may choose tenant/landlord while incomplete through `set_onboarding_role()` only; completed profiles, admins included, may add a tenant/landlord role through `grant_user_role()` (never `admin`). Admin promotion uses a trusted database-operator connection (see `docs/admin-provisioning.md`); never add a direct client-side role update or admin registration option.
- Address data is generated and nested, never hand-edited: `packages/constants/src/address/ph-addresses.ts` holds every province → city/municipality → barangay of the PSA's PSGC (Metro Manila is the NCR; BARMM's Special Geographic Area clusters sit under Cotabato), built by `scripts/address/build-address-data.mjs` from the PSGC Cloud API (`scripts/address/fetch-psgc.mjs` downloads the inputs, about 20 minutes at the API's 120 requests a minute). Many city names repeat (several San Fernando and Santa Cruz), so barangays are keyed by province **and** city: pass the province, `getBarangaysByCity(city, province)`, in every form that lets the user pick one. Without a province it answers only for Metro Manila or a name just one province has, and returns `[]` for an ambiguous one rather than guessing. `CITIES`, `PROVINCES`, `getCitiesByProvince` derive from the same table, so the sign-up, Complete Profile, Edit Profile and mobile profile forms cannot offer different places. The CAMANAVA listing rules (`CAMANAVA_CITIES`, ZIP blocks, `validate_camanava_location`) are separate and unchanged. City labels keep the spelling the app already stored (the generator's `CITY_LABELS`); add an entry there before renaming one.
- Postal code (ZIP) rules are shared and data-driven, never re-implemented per form: `isZipPlausibleForCity(city, province, zip)`, `getZipCityWarning(city, province, zip)` and `getPostalCode(city, province?)` (`@repo/constants`, `zip-match.ts`) back web sign-up/Complete Profile and mobile profile details, and `usePHPostalCode` (`@repo/hooks`) wraps them. A well-formed ZIP we do not recognize for the city is only a non-blocking warning (`getZipCityWarning`, web `getRegistrationZipWarning`, mobile `postal.warning`), because the tables are incomplete (most cities list a single ZIP); only format and the 1000-9999 range block. Listings stay strict for CAMANAVA (`isCamanavaZipForCity`). Metro Manila cities use the contiguous PHLPost blocks in `METRO_MANILA_ZIP_RANGES` (`address.ts`; CAMANAVA listing checks reuse them through `isCamanavaZipForCity`); every other city uses `PH_CITY_ZIPS` (`ph-city-zips.ts`), which is generated by `scripts/zip-codes/build-city-zips.mjs` from PHLPost's ZIP locator data plus a GeoNames-based dataset for provinces the locator page no longer lists (the script header says where to download both). Never hand-edit the generated file. A city with no published ZIP gets only the 4-digit format check so a real ZIP is never rejected for lack of data. Re-run the script when PHLPost publishes changes, then `pnpm --filter web test` (`lib/zip-codes.test.mjs`).
- Sign-up birth dates use the shared `@repo/utils` `validateBirthDate` / `getBirthDateRange`: strict Gregorian date-only values between the inclusive 110-year and 18-year anniversaries of today's **Asia/Manila** date (month-end clamped), with canonical field-error messages. Web registration and Complete Profile share `RegistrationBirthDateField`; the OTP request, profile insert and completion server actions independently enforce the same rule, and typed birth-date failures stay inline rather than entering the generic error modal. The existing `guard_user_profile_values` database trigger still enforces its historical 18–120 range; aligning direct database writes with the app's stricter maximum requires a separately authorized migration, not a claim that the UI changes RLS. PH mobile is the single `validatePHMobile` rule in `@repo/constants` (with `formatPHMobileInput` for typed fields, which keeps up to 11 digits and spaces them as `0917 123 4567`; web inputs call it directly and `usePHMobileValidation` applies it for mobile; never re-implement it per form or action): it accepts only the local 11-digit form with the leading `0`, typed with or without those spaces (no `+63`, `63` or bare 10-digit input; a digits-only number under 11 gets its own `PH_MOBILE_TOO_SHORT_MESSAGE`, which the web sign-up and Complete Profile fields show inline once the field is left or a submit is tried), for any 09XX number (the whole NTC mobile range, no per-prefix allowlist, because new carrier blocks and number portability make one wrong) plus the allocated 08 blocks (0813, 0817, 0895-0899), and stores the 11-digit `0XXXXXXXXXX` form; the trigger repeats that pattern (`20261026120000_allow_all_ph_mobile_blocks.sql`) and also checks gender, mobile and 4-digit postal code on changed fields so older rows stay editable. Review shared and database rules together whenever changing a profile policy.
- A confirmed email with no `public.users` row (sign-up interrupted after the code) is recoverable, never a lockout: sign-in and boot keep the session and send it to finish the profile (web `/sign-up?from=profile-missing` → `/complete-profile`, which inserts the row when none exists; mobile `service/auth/profileMissingService.ts` → `finish-profile`, which inserts too). Suspended accounts also look profile-less under RLS, so always check `get_my_suspension_status` before treating "no row" as unfinished. A failed profile write after the code signs the session out on both platforms.
- Sign-up auth rules are shared, never re-implemented per platform: the password policy (`getPasswordRequirements` / `meetsPasswordPolicy`, `@repo/constants`; enforced by web `validateForm` on the server and by the shared requirement list), the duplicate-email check (`is_email_registered` RPC, counts confirmed Auth accounts without a profile), and the friendly wording for Supabase throttle/rate-limit errors on code requests (`getEmailCodeRequestError`, `@repo/utils`). An account whose email was never confirmed is not a dead end: sign-in offers a new code (web `useConfirmEmail` modal, mobile `otp-verification?mode=confirm`), and a verified code continues at finish-profile.
- Signed-out (`anon`) reads of `public.users` are column-scoped to display fields (id, names, avatar/background, roles, account status, created date) by `20261024120000_restrict_anon_profile_columns.sql`: the landlord/tenant SELECT policies make every row visible, so the grant is what keeps email, mobile, birth date and address private. A public page must never select more than those columns (or `select *`) from `users`; signed-in roles still read full rows through RLS, so new cross-user reads should pick columns deliberately.
- Admin two-step login (web only; admins are blocked on mobile): `requireAdmin` enforces a verified TOTP session (`aal2`, read from verified token claims via `lib/server-admin-mfa.ts`, decided by the pure `adminMfaDecision` in `lib/admin-mfa.ts`) behind the `ADMIN_MFA_REQUIRED=true` flag; `/two-step-login` enrols or challenges, Settings → Security lists devices and adds backups. Keep admin entry points going through `requireAdmin`. The database repeats the check: `private.has_admin_second_step()` (JWT `aal` claim) is part of `private.is_admin()`, the admin-only RLS policies and every `admin_*` / `get_admin_*` function, and any new admin check must call it (the migration is `20261024140000_require_admin_second_step.sql`; `notify_*` triggers that pick admin recipients and `admin_set_user_access`'s target-account check deliberately do not). Emergency switch-off is redefining that one function — see `docs/admin-provisioning.md`.
- Passport scope: one wallet per account (`passport_documents.user_id`, the internal `users.id`), shared by both portals of a dual-role user. The account's verified ID (the primary row and any duplicate linked to the same verification) shows in the Government ID card of both portals and never in the supporting list. Supporting documents follow the portal through `selectSupportingDocuments(documents, portal)` (`@repo/passport`, using `isDocumentTypeForPortal` from `@repo/constants`): ownership types in the landlord wallet; tenant and legacy types in the tenant wallet; NBI Clearance in both.
- Passport one-per-type rule: a user holds one supporting document per type (identity rows are separate). New duplicates are refused by the `guard_passport_document_unique_type` trigger (a trigger rather than a unique index, because legacy duplicates already exist and nothing was deleted). A new copy goes through the caller-bound `replace_passport_document()` RPC (web `replacePassportDocument`, mobile `useReplacePassportDocument` via `upload?replaceId=`): the file is uploaded first, then the RPC swaps it in and resets the document to unverified (review fields and rejection reason cleared), lifting `sync_passport_document_review`'s owner content lock only through its transaction-local `app.passport_replace` flag. The replaced file is removed unless an active application still references it. Pickers disable already-added types (`getAddedSupportingDocTypes`); migration `20261028150000_passport_one_document_per_type.sql`.
- Landlord-side features require a verified account: a user holding `landlord` whose `account_status` is not `verified` (unverified, pending, rejected) cannot create or change listings, photos, applications, visit requests, tenancies, maintenance requests, payments, finance records or landlord chat, and cannot read the landlord side of those tables. Enforcement is `20261028160000_verified_landlord_gate.sql`: `app_private.unverified_landlord_id()` (null for verified accounts, other roles and service role), the `guard_verified_landlord_write` triggers (they fire inside SECURITY DEFINER RPCs too, because identity comes from the JWT), the restrictive "Verified landlords only" SELECT policies and the storage policies for `apartment-images` / `signed-leases`. The block is scoped to rows where the caller is the landlord, so a dual-role account keeps tenant-side access, and landlord-only chats are blocked outright while dual-role chats are blocked only about their own apartments. Listings of a non-verified landlord are also not public: `20261028170000_hide_unverified_landlord_listings.sql` adds restrictive apartment SELECT policies (`public.is_landlord_account_verified`) that reuse the admin-hide participants (`can_view_hidden_apartment`: the landlord, tenants with a tenancy there, admins); images, applications and visits close with the listing and verifying the landlord restores it. Notifications and push are never suppressed for these accounts: the verification result (`notify_verification_reviewed`) must reach them. Clients mirror it with `canUseLandlordFeatures` / `isLandlordAccessBlocked` (`@repo/utils` `landlordAccess.ts`): web `requirePortalViewer("landlord")` redirects to `/landlord/verify-required` (public listing views pass `true`), `LandlordAccessGate` in the landlord layout renders the wall on every other route, and mobile wraps the landlord tabs and `app/landlord/_layout.tsx` in `LandlordVerificationGate`. Tests: `pnpm db:landlord-gate:test`.
- Tenant-side actions require a verified account too: a user holding `tenant` whose `account_status` is not `verified` may browse, edit the profile, verify and use favorites, and nothing else (`20261028180000_verified_tenant_actions.sql`: `guard_verified_tenant_insert` blocks new visit requests, maintenance requests, payments, reviews and chat messages; applications already require verification). Only inserts are blocked, so cancelling or reading existing rows never gets stuck. Payments and maintenance requests are exempt for the tenant's own active tenancy (see below). Clients surface the database message ("Verify your account to use this feature.") as-is. A running tenancy is never stranded (`20261028190000_active_tenancy_exemptions.sql`): while a tenancy is active, the gates step aside for that tenancy's own rows only. The tenant can still pay and report maintenance (`tenant_has_active_tenancy`), and the landlord can still confirm cash, answer maintenance and end the tenancy (`landlord_has_active_tenancy`, and the tenancy row itself while its status is `active`; its read policy is dropped because Postgres checks restrictive SELECT policies against the updated row). Everything else stays closed (new listings, applications, visit requests, new tenancies, finance records, chat). The `paymongo` edge function needs no extra check: its active-tenancy lookup is the gate. Web (`isLandlordRouteOpenWhileUnverified(path, hasActiveTenancy)`, `LANDLORD_TENANCY_PATHS`) and mobile (`LandlordVerificationGate allowTenancyScreens`, `useHasActiveTenancy`) keep the Payments and Maintenance screens open for such a landlord. Tests: `pnpm db:landlord-gate:test`.
- Verified landlord badge: a landlord's Passport holds ownership documents (`LANDLORD_DOCUMENT_TYPES` in `@repo/constants`; the picker is portal-aware via `getDocumentTypesForPortal`). Passport rows stay private, so public pages read only the yes/no `get_verified_landlord_ids()` RPC (security definer, anon + authenticated, max 200 ids): an admin-approved (`review_status = 'verified'`), unexpired ownership document of a non-suspended landlord. NBI Clearance is identity, not ownership, so it never earns the badge. Web uses `lib/verified-landlord.ts` (profile trust strip + apartment landlord card); mobile uses `useVerifiedLandlord` and `VerifiedLandlordChip`. A failed lookup shows no badge. The public landlord profile (web and mobile) also lists a "Verified on APT Passport" card: every ownership document the landlord added, each with a verified / not-verified icon, through `get_landlord_ownership_documents()` (type name and a flag only, never files; rejected, pending and expired all read as not verified; `sortLandlordOwnershipDocuments` puts verified first). Migrations: `20261028120000_verified_landlord_ownership.sql` and `20261028140000_landlord_ownership_documents.sql` (which replaces the earlier verified-only function); apply them before the badge or card can appear.
- App releases (`public.app_releases`, one `android` row: latest/required version, https APK link, notes): readable by `anon` and `authenticated` on its public columns only (`updated_by` stays private); clients never write it. Admins publish through `admin_publish_app_release()` (calls `private.is_admin()`, so the second step applies), surfaced on web at `/admin/app-updates` via `app/admin/actions/app-release.ts`. Each publish that changes a value also appends a row to `app_release_history` (admin-only read through `private.is_admin()`, no client writes); re-saving the live values is not logged, and the page lists the history newest first beside Live release, What users see and Release checklist cards. The Live release link check runs on the server (`lib/app-release-link.ts`): HEAD only, redirects followed hop by hop, public https hosts only (never IP literals or internal names), streamed behind `Suspense`. The rules (`major.minor.patch`, required ≤ latest, https link, 1,000-character notes) live in `@repo/utils` `appRelease.ts` and are repeated by the table checks. See `docs/app-updates.md`.
- Account suspension is **app-level**: `public.users.is_suspended` (+ `suspension_reason`) is the source of truth, enforced by the restrictive `Active accounts only` RLS policies and the `admin_set_user_access()` RPC (admin-only, audited, deletes sessions). Never use Supabase Auth's `ban_duration`; suspended users authenticate normally, and clients read their own state via `get_my_suspension_status()` to show the notice (mobile `suspensionService`/`useSuspensionGuard`, web `/suspended`). Service-role code paths (edge functions, notification push) must check `is_suspended` themselves.
- When a table has multiple FKs to `public.users` (e.g. `reviews`, `chat`), disambiguate joins explicitly: `users!reviews_tenant_id_fkey`.
- Use DB migrations for schema changes; direct SQL only for read-only queries or one-off DML.
- Demo activity is managed only by `pnpm db:populate` (`scripts/db-populate/`, private `demo_population` schema), never client-facing RPCs or blanket resets. It reuses existing users/listings, freezes one deterministic rental dataset plus a separately tracked finance component, tracks inserted rows and allowed apartment patches, and refuses reset/cleanup after edits or new dependencies. `--finance --run <id>` can add expenses/budgets to an applied rental run without rebuilding/rebaselining its plan or relaxing its drift checks; existing reviewed/manual finance months are preserved, and new review confirmations block finance cleanup. Fresh populations include both components atomically. Generated payments carry `APT-` + eight capital letters or digits references (a pure function of the stable payment ID); runs saved earlier with `DEMO-` references are switched only by `--rekey-references`, which touches nothing but those references (see `docs/demo-population.md`). Hosted writes require a reviewed preview token and explicit project confirmation; do not run them as part of implementing the tool. Keep integrity triggers enabled and review the importer audit hashes when trigger bodies change. See `docs/demo-population.md` for setup, limits and tests.
- Before remote backend operations, confirm the target against the active app's public Supabase URL; the CLI link can point to a different project. Profile UPDATE must stay column-scoped: after removing a broad table grant, explicitly retain the intended profile/onboarding columns and `updated_at`, never `email` or server-managed identity/access fields. Owner-only and active-account RLS still apply.
- `apartments` INSERT is column-scoped like UPDATE: clients never set `is_verified`, moderation (`is_hidden_by_admin`, `hidden_*`), ratings/counters or timestamps. New client listings are forced to `status = 'available'`, `is_verified = false` (verification is `is_verified` + `apartment_verifications`; `status` is occupancy only, and clients may not set `unverified`). `apartment-images` uploads are landlord-only and deletes owner-only.
- Storage buckets are private by default; store **storage paths** (not public URLs) in DB columns, generate signed URLs on read. **Exception:** `apartment-images` is **public** (`public=true`, 10 MB limit) — `apartment_images.url` / `url_thumb` store permanent CDN public URLs (`getPublicUrl`) and render via `expo-image cachePolicy="disk"` with no signing (verified `storage.buckets.public=true` on `apartment-images`).
- Messages list state is server-side and per user: `conversation_preferences` (pin, archive, mute, marked unread) is written only through `set_conversation_preference` / `mark_conversation_read`; blocks (`user_blocks`, messaging only) through `block_user` / `unblock_user` and enforced by the `guard_chat_blocks` trigger in both directions — `block_user` refuses while the two share an active tenancy (mute/report instead; unblocking is always allowed); reports (`user_reports`) through `report_user`, reviewed by admins via `admin_resolve_user_report`. Clients never write these tables directly, and block/report DB messages are user-facing.
- Signed lease is one executed contract per tenancy, private to its landlord and tenant (never admins): the file lives in the `signed-leases` bucket at `{tenancyId}/{ts}.{ext}` and the row fields (`tenancies.signed_lease_path`, `signed_lease_uploaded_at`, `signed_lease_uploaded_by`, `tenant_acknowledged_at`) are written only through the caller-bound `set_tenancy_signed_lease` / `acknowledge_signed_lease` RPCs — `guard_tenancy_signed_lease_fields` rejects direct client writes to those four columns, because `authenticated` holds table-level UPDATE on `tenancies`. Storage policies scope that folder to the tenancy's landlord (upload/delete, active tenancy only) and to its landlord or tenant (read); replacing the file deletes the replaced object and resets the acknowledgement, so it always refers to the current document. Web only: landlord uploads from My Properties → Tenant Information, tenant reviews and confirms in My Rental → Signed lease (toast nudge; no notification trigger).
- Maintenance fees belong to the tenancy that raised them (`maintenance_request.tenancy_id`, set by trigger on insert and immutable). Bills and legacy fee reads scope by tenancy, so re-letting a unit — even to the same tenant — never inherits an older unpaid fee; fees with no resolvable tenancy stay unbilled. `fee_status` is `pending → paid | waived` and never reopens. Landlords waive a pending fee through the caller-bound `waive_maintenance_fee` RPC (pending-only; refuses a fee reserved by a pending payment); `paid` remains payment-trigger-owned. `guard_maintenance_fee` blocks a tenant's direct table write of `fee_status = 'waived'` or `fee_amount`, so the RPC is not the only line of defense. Ending a tenancy requires settling or waiving its pending fees (`guard_vacate_pending_fees`).
- Maintenance resolution fees are optional and written atomically with the landlord's resolution notes/status, never as a second request. Reuse the validation/status helpers in `@repo/utils` (`maintenanceFee.ts`); preserve `waived` on reads rather than treating it as pending. Mobile maintenance mutations refresh exact affected caches and guard retired-account rollbacks. Maintenance is not currently Realtime-published: use the existing focus refresh path, not an unpublished table binding. See ARCHITECTURE.md §12 and DESIGN.md for behavior and presentation.
- Notifications are generated **server-side only**: DB triggers insert into `notifications` via `create_notification()` (which also fires the `push-notify` edge function through pg_net). Clients only SELECT their own rows and UPDATE `is_read` — never INSERT. Expo push tokens live in `push_tokens`: register through the caller-bound `register_push_token()` RPC so a token can move between accounts on one device without loosening owner-only table RLS; delete on sign-out.
- Auth email templates live in `supabase/templates/` (mirrored in `config.toml`) and reach the hosted project only via `supabase/templates/build-payload.py` + Management API `PATCH .../config/auth` — never `supabase config push` (it would push local-only auth settings) and never print the full response (it contains SMTP credentials). Never embed fonts in templates: emails over ~102 KB are clipped by Gmail and hide the code. See ARCHITECTURE.md §4.5.
- `create_notification()` EXECUTE is revoked from `authenticated` — only SECURITY DEFINER triggers (and service_role) call it. Trigger functions identify the acting user via `auth.uid()` (PostgREST JWT GUC), e.g. to skip self-notifications (tenant self-cancel of a visit request).
- Message reactions notify the reacted-to message author through the same path: `notify_chat_reaction()` (`after insert on public.chat_reactions`, SECURITY DEFINER, migration `20261017090635`). It reuses `type = 'message'` so the per-type preference, the message icon/colour, the `screen: 'chat'` portal audience and the in-conversation toast suppression all apply unchanged. Only the message author is notified (never a self-reaction, never a non-participant), muted conversations and either-direction `user_blocks` are skipped, and it is INSERT-only with a 15-minute per `(recipient, message, reacting user)` cooldown — so replacing an emoji or remove/re-add toggling cannot spam. The OS push body is the reaction sentence only; the short message preview rides `data.messagePreview` (server-truncated, one line) and is rendered in-app by `getNotificationPreview` (`@repo/utils`) as a quoted line in the web drawer row and the mobile `NotificationRow`.
- `push-notify` includes `notificationId` in the push payload `data`; clients mark the feed row read on tap or banner action (fire-and-forget) so the in-app unread count stays accurate.
- Trigger payloads include the `apartmentId` needed to resolve deep links (payment, maintenance); never rely on payloads without it.

## Engineering Philosophy

- Prefer reuse over duplication.
- Extend existing components before creating new ones.
- Minimize custom implementations — let HeroUI / shadcn / platform primitives do the work.
- Keep Web and Mobile behavior aligned (mobile-first; web mirrors its semantics).
- Prioritize readability over cleverness.
- Type safety over convenience.
- Keep business logic separate from UI.
- Prefer composition over inheritance.
- Optimize for maintainability.

## Architecture Principles

- Shared logic belongs in `packages/`; platform-specific code stays inside `apps/`.
- UI components remain presentation-focused.
- Business logic belongs in hooks/services, not components.
- Database logic belongs in Supabase (RLS, policies, migrations) — not in client code.
- Never duplicate validation logic — use `@repo/hooks` / `@repo/utils` / `@repo/constants`.
- Keep state as local as possible (see State Management Rules).

## Decision Hierarchy

When multiple solutions are possible, follow this order:

1. Reuse existing code.
2. Extend an existing implementation.
3. Share code between platforms.
4. Create a new abstraction.
5. Create a new component.

Always prefer the smallest change that satisfies the requirement. For UI-component decisions, follow DESIGN.md §21 (AI Decision Hierarchy).

## Repository Conventions

### Web (`apps/web`)
- Route folders kebab-case (`browse`, `forowners`); route groups in parens (`(auth)`, `(main)`); dynamic segments camelCase (`[apartmentId]`).
- App components PascalCase with `export default function`; shadcn primitives kebab-case in `components/ui/`.
- Hooks: kebab-case files (`use-favorites.ts`) exporting camelCase (`useFavorites`); `"use client"`.
- No barrel exports — components imported directly by path.
- Alias `@/*` (tsconfig); monorepo packages via `@repo/*`.
- Server actions in `app/(auth)/actions/*.ts` with `"use server"`.
- Server pages fetch and pass props to `"use client"` children; wrapper components get a `Client` suffix (`MessageClient`, `FavoritesClient`).

### Mobile (`apps/mobile`)
- Feature folders lowercase (`apartment/`, `chat/`) or kebab-case (`document-id/`); route files kebab-case (`sign-in.tsx`); dynamic routes in brackets (`[apartmentId]`).
- `components/` subfolders plural lowercase (`buttons/`, `cards/`, `display/`, `inputs/`, `layout/`); component files PascalCase.
- Hooks: `hooks/<domain>/useX.ts` camelCase files; each domain folder has a barrel `index.ts` with named re-exports.
- Stores: `stores/useXStore.ts` — `create<State & Actions>((set) => …)` with exported `interface`, `initialState`, and `reset()`.
- Import aliases mixed (`@/*` and bare `components/*`, `hooks/*`, `constants/*`, `assets/*`) — match the surrounding file.
- Components never import the Supabase client directly — hooks/services do.

### Packages (`packages/`)
- Layout: `src/` + `package.json` + `tsconfig.json`; single entry `exports` → `./src/index.ts`.
- Named exports only; barrel `index.ts` at package root (and per-subfolder where applicable).
- Cross-platform, dependency-light; platform-specific peer deps are optional.

### TypeScript
- `strict: true`. Avoid `any` — explicit typing preferred.
- `interface XxxProps` for component props; `type` for unions/statuses.
- Route-scoped shared types in `types.ts` files.
- Type-only imports: `import type { … }` or inline `type` in destructuring.
- Semicolons in app code (shadcn `components/ui/*` files omit them — don't reformat).

## Performance Guidelines

- Avoid unnecessary re-renders.
- Memoize only when beneficial (e.g. `React.memo` on heavy stable components — used sparingly today).
- Virtualize long lists (`FlatList`/`FlashList`); adopt as list screens grow.
- Lazy load heavy screens where the framework supports it.
- Cache signed URLs on read (see Supabase Conventions).
- Keep bundle size reasonable — mind the icon library mix and heavy deps.
- Avoid unnecessary network requests (reuse fetches, avoid refetch loops).
- Prefer optimistic updates where appropriate.
- Media uploads are **binary with client-side compression** (`compressImage.ts`) — never base64; apartment images are stored two-tier (thumb + full), thumbs render from the thumb column.
- Lists fetch **bounded pages** with keyset cursors — never unbounded selects (chat history: 30-message pages, descending `created_at, id`, ID-deduplicating merge).
- Public image egress is metered (Supabase Free: 5 GB cached egress per cycle): never render a public apartment photo from Supabase with a bare `unoptimized` (the browser would download the original, legacy uploads reach 3 MB) — use `unoptimized={!canOptimizePublicApartmentImage(src)}` plus a `sizes` hint so Next serves a resized copy. Uploads to a public bucket with a unique, never-overwritten path pass `cacheControl: PUBLIC_IMAGE_CACHE_CONTROL` (`@repo/constants`, one year); never use it for a path replaced in place (avatars/backgrounds on the web use a fixed path).
- External media (GIFs) are referenced by `externalUrl` on the row — no download-then-re-upload round trips.

## State Management Rules

- **Local state** (`useState` + custom hooks) is the default — use nothing else unless needed.
- **React Query** (mobile only): the standard layer for server data. Reads via `useQuery` on stable query keys; mutations via optimistic updates + exact-key `invalidateQueries`. Default `staleTime` 30s; `clearQueryClient()` on sign-in/sign-out (sensitive in-memory state — e.g. signed URLs — clears with it). Never put tokens or signed URLs in query keys; never mirror server data in Zustand.
- Read-settling mutations (mark-read, status changes) settle with exact-key `invalidateQueries({ refetchType: "none" })` — mark-stale only; the mutation's own realtime event is the single refetch trigger. UI counters (e.g. unread) update optimistically with rollback, never via extra refetches.
- **Realtime (mobile)** — one channel per user/resource identity via refcounted registries (`useNotificationRealtime`, chat channels); never one channel per consumer. Channel identity is keyed by data identity (user/peer/apartment), never by render callbacks; event callbacks flow through refs.
- **Zustand** (mobile only): client state shared across screens — form flows, theme, personalization. Lives in `stores/`; includes `reset()`.
- **Theme** (mobile): `useThemeStore` holds only the saved `system | light | dark` preference; `useThemeSync()` at the root is the single place that applies it via `Uniwind.setTheme(mode)` (`system` clears the override and follows the device) and keeps the splash up until the saved choice has loaded. Read the resolved palette with `useColors()` (Uniwind's active theme); read/set the preference with `useThemePreference()` only where needed. Mobile neutral roles live in `constants/theme.ts`, mapped in `app/global.css` and checked by parity/contrast tests; the `light` and `dark` `@variant` blocks must declare the same variable names (Uniwind fails the bundle with "Theme <name> is missing variable" otherwise), which `constants/theme.test.ts` enforces; shared brand/status colors remain in `@repo/constants`. See DESIGN.md §3 for values. Never call `Appearance.setColorScheme()` from components or hooks.
- **Portal preference** (mobile): `users.roles` is server-authoritative; `usePortalStore` holds only the active tenant/landlord navigation choice in memory. Persist that choice per auth user in AsyncStorage across sign-out, but clear in-memory state and React Query on sign-out/account change. Always validate the saved choice against the latest roles before routing; never persist roles or treat a preference as authorization.
- **Boot prefetch** (mobile): `app/index.tsx` loads the profile into `CURRENT_USER_QUERY_KEY` (the tabs layout reuses it) and, for the tenant portal, `prepareTenantHome` starts the Rentals queries under their hooks' own keys. A failed prefetch is reset, not left as an error. The Rentals skeleton shape comes from a per-account AsyncStorage layout hint (`service/tenancy/rentalsLayoutHint.ts`): a UI hint only, never shown as data or used for access.
- **Supabase** is the source of truth for all server data; fetch in hooks/services behind React Query — never mirror it in stores.
- **Server data (web)**: data hooks load through `hooks/use-async-resource.ts` (memoized loader → `{ data, loading, error, refresh, revalidate, setData }`); effects never set state synchronously (`react-hooks/set-state-in-effect` is enforced in CI). `refresh()` shows the loading state; `revalidate()` refreshes in the background without a skeleton or error takeover, so focus/visibility refetches never remount the screen. Browser-only values use `useSyncExternalStore` (`use-hydrated`, `use-mobile`); prop-to-state resets compare with the previous prop during render instead of an effect.
- **Initialized resources (web)**: an explicit `useAsyncResource` seed is fresh server-request data, never a cross-request cache; it settles the initial loader instead of immediately fetching the same data again. Financial data stays independently loaded. Sensitive resources opt into clearing data on background failure; session/resource changes retire old reads and mutation callbacks. A successful mutation should reconcile without a blocking full-page refresh and keep its submission lock until reconciliation settles. See ARCHITECTURE.md §12.
- **Server identity and presentation seeds (web)**: compatible layouts and loaders share `lib/server-identity.ts` (`React.cache`, authoritative `getUser()` plus a caller-owned profile read, scoped to one React request only). `requirePortalViewer` settles role, suspension and onboarding checks before private presentation queries; middleware/recovery and server-action authorization remain independent. Seeded routes use the same service query/mapping with an injected cookie-bound client, never a browser client on the server. `PresentationBoundary` (or My Rental's account-keyed boundary) retires seeds, drafts and callbacks on Auth ID/generation/resource/request changes. Seeds contain paths, never signed private URLs, and must preserve the existing complete-list/limit contract. My Rental streams the applications seed into its own `Suspense` region; bills and payment history remain unseeded. See ARCHITECTURE.md §12.
- **Route streaming (web)**: server pages settle Auth/role guards and only the data needed to describe the page, return the shell, then stream independent reads from async child components behind `Suspense`. Never await a secondary query at the top of a page when the page can render without it. Fallbacks mirror the loaded region and carry no private data; when a route's `loading.tsx` and its in-page fallback cover the same region they share one skeleton component, otherwise the route skeleton mirrors the page shell. Browse's filtered rail, mobile filter entry and grid share one request-scoped `loadBrowseResults` (`React.cache`); Profile streams verification activity into `PassportProfileCard`'s `verificationSlot` while `account_status` stays immediate; My Rental keeps `fetchTenancyContext` and fresh, caller-bound `fetchTenancyFinance` separate, with payment actions behind authoritative finance; both Messages portals stream contacts behind `MessagesRouteSkeleton` after authorization. See ARCHITECTURE.md §12.
- **Opt-in browser presentation reuse (web)**: `useBrowserResource` is a narrow `useSyncExternalStore` exception, not a cached default for `useAsyncResource`. Only Favorites card presentation currently opts in. The browser-only store keys Auth ID + internal profile ID + portal + resource + canonical filter/page cursor, reuses fresh data for 30s, rejects it after 120s and keeps at most 20 LRU entries; loaders must bound their payloads (Favorites: 50 rows, one public cover per listing). Stale revisits/refocus revalidate without replacing cards; failed refreshes retain usable data with Retry. Root Auth lifecycle, auth/recovery/suspension navigation and client sign-out retire account data and late requests; favorite services invalidate affected pages after successful writes. Never use this store for roles/access, verification, active tenancy, bills/payments, application decisions, private signed URLs or maintenance-action authorization. See ARCHITECTURE.md §12.
- **URL state** (web): filters and search via `searchParams` / `useSearchParams`. Admin list pages share `useListFilters` (`app/admin/_components/filters/use-list-filters.ts`): applied filters show optimistically (`useOptimistic`) while the server re-renders, search applies debounced with `router.replace`, and local state syncs from props during render — never remount the client with a filter-derived `key`.
- **Context** (web): none for session state — `AuthContext` is form-state scoped to the `(auth)` route group only. Session awareness comes from `hooks/use-user.ts` (with `onAuthStateChange`) and server pages. Avoid adding global contexts.
- Never duplicate state: derive from a single source, reset stores on completion, keep stores out of server data.

## Component Guidelines

- **Mobile finance (`apps/mobile/components/finance/`):** each production `.tsx` file declares one React component, including private helpers, default-exported with a matching PascalCase filename. `react/no-multi-comp` enforces the component count in mobile lint; filename/export conventions are checked in review. Props, local constants and small pure helpers may stay beside their component; shared non-component code belongs in focused `.ts` modules, and substantial form logic in `hooks/finance/`. Import components directly, never through barrels. Tests may declare multiple mock components; ordinary render callbacks and inline JSX do not require extraction. Split by responsibility, not an arbitrary line limit.

Before creating a component, ask:

- Does one already exist (app, `packages/`, HeroUI, shadcn)?
- Can HeroUI (`@heroui/react`) / HeroUI Native (`heroui-native`) solve this?
- Can it be shared between platforms (goes in `packages/`)?
- Is it platform-specific (stays in `apps/`)?
- Is it reusable, or should it stay route-scoped?

Follow DESIGN.md §22 (Before Creating a New Component — Checklist) for the full UI-side checklist.

## Continuous Plan Execution

When asked to implement any Markdown plan file, such as PLAN.md, FIX_PLAN.md, IMPLEMENTATION_PLAN.md, REFACTOR_PLAN.md, or similar:

1. Treat the entire plan as one continuous task.
2. Complete all unfinished, feasible tasks.
3. Do not stop after one task, phase, or section.
4. After completing one item, immediately continue to the next.
5. Do not ask "Should I continue?" between tasks.
6. Continue until all implementable tasks are completed and verified.
7. Ask questions only when genuinely blocked by a decision, missing requirement, permission, credential, or external dependency.
8. Prefer concise multiple-choice questions when appropriate, with the recommended option first.
9. Questions are temporary interruptions. After the user answers, immediately resume the remaining plan.
10. If a safe choice can be inferred from the repository, conventions, documentation, or surrounding code, make that decision yourself.
11. Do not leave TODOs, placeholders, mocks, or incomplete work that can reasonably be finished now.
12. Inspect existing code before modifying it and preserve working behavior unless the plan requires otherwise.
13. Follow repository instructions, architecture, and coding conventions.
14. Run relevant type checks, linting, tests, builds, and project-specific verification.
15. Fix errors introduced by the implementation before finishing.
16. Re-read the entire plan before declaring completion and confirm no feasible unfinished tasks remain.

Only stop when:
- every feasible task is completed and verified, or
- progress is genuinely blocked by user input or an external dependency.

Progress updates are allowed, but they must not interrupt implementation.

## Graphify

This project uses a local knowledge graph at `graphify-out/` with god nodes, community structure, and cross-file relationships. The root output directory is generated and ignored by Git; it is not an application, build, test, or CI dependency. Keep `.graphifyignore` and the OpenCode plugin tracked, but never force-add generated root snapshots.

On a fresh clone, install the Graphify CLI if needed (`uv tool install graphifyy`, or `python -m pip install graphifyy` in a virtual environment), then run `graphify extract . --code-only` from the repository root. This bootstraps code navigation locally without an API key; it does not recreate semantic document/image knowledge. Existing local semantic knowledge is retained by normal updates. For full semantic extraction, use the Graphify skill. See `docs/graphify-conflict-audit.md` for rollout and branch-switch precautions.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

**Graphify is the default navigation mechanism** — run it before repository-wide searching (grep) for any codebase question.

Choosing the right command:

| Goal | Use |
|---|---|
| Codebase question ("how does X work?") | `graphify query "<question>"` |
| Focused concept, component, or feature | `graphify explain "<concept>"` |
| Relationship between two files/concepts | `graphify path "<A>" "<B>"` |
| Broad navigation / first look at the repo | `graphify-out/wiki/index.md` (if present) |
| Broad architecture review, or when query/explain/path surface too little | `graphify-out/GRAPH_REPORT.md` |

These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.

Rules:
- Generated local graph files are expected after hooks or incremental updates and must stay untracked. Staged root graph deletions during the one-time untracking rollout are expected; after that commit, regeneration must not dirty Git status. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- After modifying code, run `graphify update .` from the repository root to keep the graph current (AST-only, no API cost). Do not regenerate legacy nested `apps/*/graphify-out/` snapshots; their separately tracked history is outside the local-root workflow.
- After pulling or switching branches, refresh the local graph before relying on it. Do not install auto-commit/force-add hooks or merge drivers for ignored outputs; never hand-merge generated graphs. Older branches may need a one-time modify/delete conflict resolution by keeping the root snapshots untracked.
